# Pilot round 7 — ADD at low effort against raw Claude Code at medium (2026-10-02)

**Question.** On the same model (`claude-sonnet-5-5`), does ADD at `--effort low` deliver the
quality that raw Claude Code delivers at `--effort medium`, and what does it cost? Does the
prompt-audited skill (`PROMPT-AUDIT-2026-10-02.md`) do better than the shipped one at low effort?

**Arms** (harness `fae22f71`, workloads wm1 and amb1, **n = 3 per arm per workload — directional,
not significant**):

| arm | skill | effort |
|---|---|---|
| `vanilla` | none (raw Claude Code) | medium |
| `add-4` | ADD 4.0 as shipped | medium — the effort reference |
| `add-4-low` | ADD 4.0 as shipped | **low** |
| `add-4-audited-low` | ADD 4.0 + the audit diff | **low** |

Every arm loads the operator's `~/.claude`, as in rounds 4–6 (audit finding 9).

## Metrics — fixed before the results were read

### Quality: did the user get a working, correct app?

| # | metric | how it is measured | workload |
|---|---|---|---|
| Q1 | **Delivered** | the run ends with an app the oracle can start and use (`oracle_pass_rate > 0`). A run that halts to ask a question counts as not delivered, because the run is headless | both |
| Q2 | **Oracle pass rate** | the share of the official checklist that passes (`metrics.oracle_pass_rate`) | both |
| Q3 | **Held-out edges** /22 | probes the agent never saw: a malformed body (not JSON, `null`, a number, a list), wrong types, non-positive or fractional durations, timestamps with an offset and with `Z`, invalid status on create and on PATCH, a double DELETE, and the app still answering at the end. A 5xx or a dropped connection fails the probe | wm1 |
| Q4 | **Ambiguities handled** /7 | planted ambiguities whose verdict is `surfaced` or `guessed_right`, as `benchmark/ambiguity.py` scores them (the round-6 definition). **Surfaced** is also reported on its own | amb1 |
| Q5 | **Test strength** | mutation score: the share of scripted mutants of the app's own code that its own tests kill. Mutants flip comparisons (`<`↔`<=`, `>`↔`>=`, `==`↔`!=`), `and`↔`or`, and `True`↔`False`, with at most 12 per run. A run with no tests scores 0 | both |

### Trust: can the human believe what the run claims?

| # | metric | how it is measured |
|---|---|---|
| T1 | **Seal intact** | `git diff <freeze> HEAD -- <the task file>` is empty (ADD arms only) |
| T2 | **Verdict recorded** | a `verify(<slug>): PASS` or `RISK-ACCEPTED` commit exists (ADD arms only) |
| T3 | **Evidence matches a rerun** | the pass count claimed in `## EVIDENCE` equals the count from rerunning the workspace's tests (ADD arms only) |
| T4 | **Own tests written** | the number of `def test_` in the workspace. This is context, not a score: more is not better |

### Cost: what did it take?

| # | metric | source |
|---|---|---|
| C1 | **Cost per run** (USD) | `metrics.cost_usd` |
| C2 | **Wall time** (min) | the transcript's `result.duration_ms` |
| C3 | **API messages** | assistant messages, deduplicated by message id |
| C4 | **Output tokens** | the transcript's `result.usage.output_tokens` |
| C5 | **Cost per delivered run** | total cost ÷ runs with Q1 true. This is the headline cost: a cheap run that halts is not cheap |

### Decision rules (n = 3, so these are directional)

1. **ADD-at-low holds** if it matches or beats `vanilla` at medium on Q1, Q2 and Q3/Q4, with no
   single run worse than vanilla's worst. It **pays for itself** if it also wins at least one of
   Q4, Q5 or T3, which are the things ADD claims to buy.
2. **Effort effect:** `add-4-low` against `add-4`. If quality is equal, low effort is the cheaper
   default only if C1 or C2 drops by at least 15%.
3. **Adopt the audit diff** if `add-4-audited-low` matches `add-4-low` on every Q and T metric and
   is no worse on C1 and C2. If quality is equal and cost is equal, it is adopted anyway for the
   high-confidence path fix alone.
