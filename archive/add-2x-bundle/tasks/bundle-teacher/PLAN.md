## 1 · SPECIFY — the rules ▸ docs/03-step-1-specify.md

Feature: Ship the vendored teacher snapshot in both the npm tarball and the pip wheel, and have `init`/`update` materialize it into a project's `.add/personas-teacher/` — with the MIT attribution riding along, the engine still NO-EXEC, and the release build still zero-network.
Framings weighed: extend the existing MANAGED twin maps + prepare_bundle (chosen — reuses the proven ship-controlled pipeline, npm↔pip parity, _bundled committed+parity-guarded) · a separate post-install fetch (rejected — breaks zero-network + engine NO-EXEC) · materialize lazily at the persona phase only (rejected — the corpus must be present after a plain install, no engine action).
Must:
<must>
  - The npm tarball contains the vendored teacher tree (the agent-def .md files + the MIT LICENSE) under `personas-teacher/`.
  - The pip wheel contains the same tree under `add_method/_bundled/personas-teacher/`.
  - The MIT attribution ships in BOTH distributions (the retained `personas-teacher/LICENSE`; and a `THIRD_PARTY_NOTICES.md` shipped in each package).
  - `init` and `update` (npm AND pip) clean-replace the snapshot into the project as `.add/personas-teacher/` — a ship-controlled tree, never user data.
  - `prepare_bundle.py` regenerates `_bundled/personas-teacher/` + the shipped NOTICES from the canonical sources; the bundle-parity guard proves no drift.
  - The committed `_bundled/` stays byte-identical to canonical (parity), carries no test/junk, and a fresh-install acceptance materializes `.add/personas-teacher/`.
</must>
Reject:
<reject>
  - The npm `files` allowlist omits `personas-teacher/` (the dir silently drops from the tarball) -> "teacher_absent_from_npm"
  - The pip wheel ships no file under `_bundled/personas-teacher/` -> "teacher_absent_from_wheel"
  - A bundle ships without the MIT notice (no LICENSE / no THIRD_PARTY_NOTICES.md) -> "attribution_missing"
  - `_bundled/` drifts from canonical, or carries a test_*.py / bytecode -> "bundle_drift"
  - Any engine code path (add.py / add_engine) gains a fetch/spawn or references update_teacher -> "engine_exec_violation"
</reject>
After:
<after>
  - A `npm pack` tarball and a built wheel each contain the teacher tree + the MIT notice.
  - A fresh `init` (both installers) leaves `.add/personas-teacher/` populated; `update` refreshes it.
  - ENGINE_MD5 + ENGINE_PKG_MD5 unchanged; the release/tag build performs no network IO.
</after>
Assumptions — lowest-confidence first:
<assumptions>
  ⚠ THIRD_PARTY_NOTICES.md must physically ship inside BOTH package roots — lowest confidence because the canonical lives at the REPO root (outside add-method/, the npm+pip package root), so it must be COPIED in (a generated, parity-guarded twin like _bundled), not referenced up a dir; if wrong (e.g. personas-teacher/LICENSE alone is deemed sufficient for the exit criterion): a redundant committed copy + parity test, cheap to drop.
  - [x] The teacher tree belongs in the ship-controlled MANAGED set (clean-replaced on update), not user data — confirmed: it is vendored/pinned, regenerated by update_teacher.py, never hand-edited in a project.
  - [x] `_bundled/personas-teacher/` is acceptable weight (~256 files / ~few MB per wheel) — confirmed: the user explicitly accepted the added bundle weight.
</assumptions>
