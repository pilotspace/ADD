## FINDINGS
- F1 (answers M1) · A "CI-only ref" inside the product repo is impossible: git exposes every ref of a remote to any reader — a read-only `git ls-remote --refs origin` here lists 350 refs including the non-heads namespaces — so the only ref a builder's checkout can lack is one in a DIFFERENT private repo, which `actions/checkout` fetches only with a PAT ("${{ github.token }} is scoped to the current repository, so if you want to checkout a different repository that is private you will need to provide your own PAT"); the encrypted-fixture route is the same fact spent differently (ciphertext in-tree, key in a secret; this repo carries no such tooling — no git-crypt/sops/age in `.github/` or root); and a third route exists: a runner whose DEFINITION the change cannot alter — `workflow_run`/`repository_dispatch` "will only trigger a workflow run if the workflow file exists on the default branch" and "is able to access secrets and write tokens, even if the previous workflow was not", and `pull_request_target` "runs in the context of the default branch of the base repository, rather than in the context of the merge commit". All three reduce to one mechanism: checks AND the runner that executes them live behind a credential or branch protection the builder lacks (A1); a receipt the builder never read IS producible by that runner · shipped needs: a holdout repo (checks + loader + runner) reachable only by a repository secret, plus a protected default branch that owns the trigger · (evidence: `git ls-remote --refs origin | wc -l` -> 350 run here; https://github.com/actions/checkout README `token`/`repository` inputs; https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows sections workflow_run, repository_dispatch, pull_request_target; `grep -rn "git-crypt|sops|age -d" .github/` -> none)
- F2 (answers M2) · The existing stamp that can carry it is `run`, executed BY THE RUNNER in its own checkout: `run()` only notarises a command it itself spawned (`subprocess.run` at add.py:4464) and writes a receipt under the task's `runs/` with `computation:` (the command line — names the holdout path, never its content), `head:` (HEAD at run start), `committed:` (scope blobs = HEAD tree), `kind: test-ids` plus passed/failed IDs only when a JUnit report was written DURING the run (a pre-dated report does not promote, add.py:4475-4487), and appends a `verified:` entry at `by: "process:run"`, authority process (add.py:4533-4553); that receipt must then travel back into the bundle by a bot commit (`ci.yml` grants `permissions: contents: read` only, lines 11-12), and once it is a file in `runs/` the gate freshness compares only `scope_digest` to the working tree (add.py:4359-4385) while the stamp is a plain string (add.py:1511) — so the record binds PRESENCE: this command, at this HEAD, over these blobs, these IDs reported; it cannot bind that the command ran in CI rather than on the builder laptop, that the holdout was unread, or that its content is what the human approved (FORMAT section 10: declared checks executed, passed, scope unchanged, rules bound — never adequacy; section 8: a refute stamp does not bind honesty or the quality of the probes). `refute --tier T4` is refused R:BADTIER because `REFUTE_TIERS = ("T1", "T2", "T3")` and the engine own comment says a T4 stamp must not claim what a prompt cannot provide (add.py:7424-7430, 7457-7459), and the gate reads neither the tier nor the signer (R:TIERJUDGED, add.py:7451) — so T4 needs a NEW claim, not a widened tier: a `verified:` entry recorded as handed, e.g. act run at authority process with an origin field · shipped needs: receipt PROVENANCE bound outside the engine — the receipt commit authored or signed by the CI identity, or an OIDC attestation of the run (this repo already holds `id-token: write` in publish.yml:115) — with the gate binding the attestation presence, never its truth · (evidence: add-method/tooling/add.py:4418-4553, 4359-4385, 1511, 7424-7459; - F3 (answers M3) · What the builder still sees or moves, per route: (i) the CHECK NAMES and their `covers:` targets are in the frozen node and `run()` keeps only the cited IDs (add.py:4508-4515), so the builder always knows WHICH property is tested, never the inputs; (ii) the CI config is a tracked file in the tree it edits and under `on: pull_request` the workflow runs in the context of the merge commit — the builder own edit to the runner is what runs; (iii) in the encrypted-fixture route the ciphertext size, the fixture path and the LOADER that decrypts it are all in-tree and builder-writable (skip-on-missing-key, monkeypatched decrypt); (iv) the receipt file itself is hand-writable and freshness cannot tell (F2).
