01Reason

One response was never
going to be enough.

A single model call is a closed system. Whatever is in the prompt is the entire world: it cannot look anything up, cannot open the file it is about to change, cannot run what it wrote, and cannot check its own claim. For a definition or a first draft, that is plenty. For work that has a correct answer, it is a guess with excellent grammar.

And the guess does not arrive hedged. It arrives confident, complete-looking, and occasionally subtly wrong — built on an assumption nobody stated, missing an edge case nobody named. A model is fast in whatever direction it is pointed, and a single response gives you no way to check the direction. One ordinary request shows the difference.

It opened the real files, wrote against the real database layer, ran the real suite, watched itself fail, read why, fixed it, and ran again. None of that is available to the panel on the left at any price.

And every line of it is still in the window. Eight turns bought a working feature and spent 15.9k tokens that never leave. Turn counts and token deltas are illustrative of the shape, not a measurement.

The ladder Anthropic names: an augmented LLM (retrieval, tools, memory) → a workflow (calls orchestrated through predefined code paths) → an agent (the model directs its own process and tool use). The left panel cannot be prompted into the right one, because what it lacks is not phrasing — it is the ability to act and then look at what happened.

Agents can be used for open-ended problems where it's difficult or impossible to predict the required number of steps, and where you can't hardcode a fixed path.

Anthropic · Building effective agents

So the question was never whether to go agentic. It is what breaks once you do — and the answer is already visible in the right-hand panel, in its last column. Hold on to this request: it comes back in act 06, run a third way.

02Reason

Then autonomy ran into
its own ceiling.

An agent buys autonomy with turns, and every turn spends context. Anthropic names the resulting decay context rot, and is precise about why it is not a limitation waiting on a bigger window: in a transformer every token attends to every other token — n² pairwise relationships — and models are trained predominantly on shorter sequences, carrying fewer specialised parameters for context-wide dependencies. The attention budget depletes as tokens arrive. It is architectural.

As the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases.

That curve stays abstract until you have watched it happen. Anthropic ran current Claude models as long-running coding agents and published the failure modes they kept hitting. Read them as the clinical presentation of everything above.

“the agent tended to try to do too much at once — essentially to attempt to one-shot the app. Often, this led to the model running out of context in the middle of its implementation, leaving the next session to start with a feature half-implemented and undocumented.”

Anthropic's own remedies land somewhere worth noticing: a structured feature list carrying explicit pass/fail state, commits with descriptive messages, a progress file, verification at the start of a session, and a clean state enforced before it ends. That is not a prompting technique. That is a record kept outside the model — arrived at independently, under the same pressure.

03The gap

Every strategy manages size.
None assigns authority.

A real discipline grew up around this. Anthropic defines context engineering as curating and maintaining the optimal set of tokens during inference, and names four strategies — every serious agent harness now ships some mix of them, including the one you are using.

Compaction is lossy on purpose, and it is loss of the right kind — until you ask which surviving sentence you are still bound by. A summary is the agent's account of what happened, and an account has no signature on it.

Persistent memory solves recall completely and ownership not at all. Notes the agent wrote are notes the agent can quietly rewrite — and the rewritten file reads exactly as authoritative as the original did.

Clean windows are genuinely the right architecture — and then the orchestrator has to accept what comes back. A condensed report about work you cannot see is a claim, not evidence. Nothing in the return channel carries a test id.

The most efficient of the four, and the clearest about the shape of the hole. Retrieval decides what is relevant, never what is settled — and a three-week-old approved contract scores lower than this morning's chatter.

The missing primitive is not more memory. It is a decision the agent is not permitted to edit.
04Resolve

ADD is that primitive,
plus the record it lives in.

AI-Driven Development is a method the agent runs off disk. You own the two things it cannot own — deciding what to build and verifying it is correct — and it owns everything in between. It installs as a skill plus a stdlib-Python kernel and drives under Claude Code, Codex, Cursor, Copilot, Gemini CLI and the rest, through one CLI.

The unit of work is one task, in one file, with eight sections. Two of them are sealed — the agent can read them, build against them, and fail against them; what it cannot do is edit them so its own work passes.

.add/tasks/transfer.md tier 1 · one feature · sealed, then closed
§1RULESwhat must hold (M) and must never happen (R)  sealed
§2ASSUMPTIONSwhat the request never said — swept across six dimensions
§3PLANthe external contract, and the file scope it may touch
§4EDGESboundary cases worth a check of their own

§6RECEIPTthe recorded run: command, exit, reported ids, scope digests
§7GATEthe outcome, who recorded it, and on what evidence
§8DELTASwhat was learned — outbound to the living specs below

But a task closes. If that were the only memory, every feature would start from zero and the project would never develop an opinion — the month-two failure again, one level up. So the bundle carries a second tier that never closes.

05Mechanism

What leaves the window,
and what comes back in.

Here is the part worth being precise about. ADD implements all four of the strategies in act 03 — it is not an alternative to context engineering, it is a concrete instance of it. Then it adds the fifth thing none of them provide. For each piece, the two columns that matter to an agent's window are what it lets you not load, and what it loads instead.

Strategy 02 Structured note-taking

PROJECT.md invariants: Project-wide constraints binding every task in the bundle, not the one in hand. Re-deriving the same global rules once per task. A thin index, read first, every session.
Strategy 03 Sub-agent architecture
add-worker One execution shell per beat: loads that beat's phase guide plus the best-fit persona and becomes the specialist. The other beats' guides, and the orchestrator's history. One guide and one persona, in a fresh window.
add-advisor The second mind: proposes a plan, pressure-tests a draft, or decides a delegable ambiguity so the beat never stalls. All the exploration that produced the advice. A recommendation, its tradeoffs, and per-dimension confidence.
Strategy 01 Compaction
SKILL.md Narrates the loop itself and pulls a deeper phase reference only when the beat needs one. A hard byte ceiling holds it there — enforced by a test, not by intent. Three of the four phase guides, at any moment. The one guide for the beat you are on.
Not on the list Authority — the fifth thing none of the four provide this
add freeze Seals RULES · CHECKS · gives: under a digest, stamped with a computed authority. The need to re-litigate a decision already made. A hash. A changed section is refused, not re-argued.
covers: bindings Every rule named by the check that proves it. Unbound rules are enumerated, not assumed. Opinions about whether the code looks correct. A rule → test-id map the engine evaluates mechanically.
add run — receipt The real command, its exit code, the ids the runner actually reported, and digests of the files in scope. The test output. The agent's account of what it ran. One recorded result — a record, not a claim.

security hard-stop A security finding is the one outcome that cannot be waived — in every mode, at every depth. The possibility of it scrolling past in a long session. A stop, with a human in the loop.

The row carrying the most weight is add gate's third column. Reviewing a four-hundred-line diff costs four hundred lines of somebody's attention budget, human or model, and pays out in plausibility. Reading a receipt costs one line and pays out in proof. That is a context strategy as much as a trust one — and the only one here that gets cheaper as the work gets bigger.

The transferable lesson, if you take nothing else from this page: the four strategies keep an agent's window small, and a small window still holds no opinion about which of its tokens you may overwrite. Durability is a separate property from size, and it has to be built separately.

06Walkthrough

One feature,
start to receipt.

Three beats, in that order, because the order is the point: no build starts until the specification and the failing tests exist, and nothing is trusted until a recorded run says so. Between your one approval and the result, the agent drives.

Why the seam sits there

Approving code after it is written is the expensive place to be wrong: the work exists, and the reviewer is reading for plausibility. Approving the contract is cheap and unambiguous — a shape, and a list of things that must never happen, agreed before a line is written to satisfy them.

BEAT 01 Direction the agent drafts · you approve once

Same request as act 01 — “let users transfer money between their own accounts”. Rules first: Musts are what it has to do, Rejects what it must never do, each carrying the error code the caller will actually see. 

## RULES
<must>
- M1 an amount moves from one of my accounts to another of mine
- M2 the debit and the credit happen in one atomic transaction
</must>
<reject>
- R:AMOUNT_INVALID an amount <= 0 must never be accepted   -> "amount_invalid"
- R:SAME_ACCOUNT   source and destination must never match  -> "same_account"
- R:OVERDRAW       a balance must never go negative         -> "insufficient_funds"
</reject>

Those are the three defects in act 01's one-call answer, now written down as rules before anything is built.

Then the section that earns its place fastest. ASSUMPTIONS records what the request never said — swept, not free-associated, because free association follows the request's emphasis rather than the risk. Every declared surface is crossed against six dimensions:

whowhose thing is it?
whichwhich ones qualify?
whenvalid at what time?
absentwhat was left out?
orderdoes sequence matter?
experiencewho lives with it?
## ASSUMPTIONS
- A1 [who]        covers: S1 · never says whether I may transfer from an account I do
     not own; taking it as own-accounts-only -> if wrong, it moves other people's money
- A4 [absent]     covers: S1 · never says what currency the amount is in; assuming one
     implicit currency -> if wrong, cross-currency transfers corrupt balances
- A5 [order]      n/a · a single transfer exposes no ordered collection
- A6 [experience] covers: S1 · never says who reads a refused transfer or what tells
     them why; taking it as the payer -> if wrong, a correct refusal reads as a fault and
     they retry until locked out

A6 is the one dimension not about correctness. A1 asks whose money it is; A6 asks who has to live with the answer — and its cost line does not describe a bug. The refusal is right. No other section has anywhere to record that.

Then the contract and the checks that prove every rule. Every M, R and E must be named by some check, or the gate refuses later and says which. 

## PLAN
contract: POST /transfers { fromAccountId, toAccountId, amount }
          200 -> { transferId, fromBalance, toBalance }
          400 -> { error: "amount_invalid" | "same_account" | "insufficient_funds" }
scope:    src/, tests/

## EDGES
- E1 a mid-transfer failure must leave both balances unchanged

## CHECKS
- test_transfer_moves_funds  · covers: M1              · balances move by exactly the amount
- test_transfer_is_atomic    · covers: M2, E1          · a mid-transfer failure changes nothing
- test_rejects_non_positive  · covers: R:AMOUNT_INVALID · zero and negatives are refused
- test_rejects_same_account  · covers: R:SAME_ACCOUNT   · source == destination is refused

Those tests get written now and must fail — there is no implementation yet, so a test that passes here is testing nothing. Red before green, enforced by the loop rather than by anyone's discipline. Now count: four checks, five rules.

.add/tooling/cli.py — transfer

Both refusals are the method working, not a tool failing. Because RULES and CHECKS are sealed, the repair is never a quiet edit — it is a visible refreeze, a re-run and a re-gate, all three recorded in the file. What you are left with is not a diff somebody skimmed: it is a record of what had to be true, what nobody said, what would have disproved it, the command that ran, the ids it reported, and the person who accepted it.
