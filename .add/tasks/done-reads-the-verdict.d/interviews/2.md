# interview 2 — done-reads-the-verdict

## A1 [who]
- asked: YES but only as a DELIBERATE ACT (`done --override "<why>"`), never from the computed floor — a gate's authority is derived, so on a security node every stop is stamped `human` and authority alone would reopen the measured walk
- if wrong: an override with no reason would be the floor granting it again, one flag over
- answered: confirm

## A2 [which]
- asked: the ones that POSTDATE the last `reopen` — the human confirmed the existing rule is right, so a reopen clears a stop and the loop's reopen semantics are untouched
- if wrong: a stale pre-reopen stop would block a reopened node forever
- answered: confirm

## A3 [when]
- asked: ONLY the seal — a stop is a RECORD against a node and a record needs the approval that says the node exists (3.3.0's argument for RISK-ACCEPTED), while every evidence refusal stays open so writing a finding never gets hard
- if wrong: refusing more would make recording a security finding the hard part
- answered: confirm

## A4 [absent]
- asked: it as CLOSING — an engine that recorded no verdict field left nodes that cannot be re-gated, so this fails open rather than stranding them
- if wrong: an unreadable verdict closes a node nobody could re-verify
- answered: confirm

## A5 [order]
- asked: the LATEST, so resolving a stop is the normal path
- if wrong: n/a, this is the measured expectation
- answered: confirm

## A6 [experience]
- asked: it as the builder who just recorded the finding
- if wrong: a refusal that only says "no" strands them
- answered: confirm
